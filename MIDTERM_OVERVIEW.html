0 · Orientation and final results

Large language models that use Mixture-of-Experts (MoE) store many big "expert" networks, but each token uses only a couple of them. Serving the model at decode time (one token at a time, per request) becomes a memory-bandwidth problem: the arithmetic is tiny, but the machine must stream huge weight matrices out of memory for very few tokens. This is the MoE memory wall. Project 2 studies it: reproduce a PIM-based fix (Duplex), quantify the wall on a single GPU, explain why the wall exists, and test whether expert accesses are predictable enough to prefetch.

The one-sentence story. Decode is bandwidth-bound; MoE expert weights are ~352 MB each and only 1–3 tokens use each one, so nearly every expert weight must be streamed from memory every step (D3). Placing them off-chip makes it worse by the link/HBM bandwidth ratio (D2, 2.72×), and a PIM die sharing the HBM is what recovers the time (D1, 3.10×). Whether that fetching can be hidden by prediction depends on routing correlation (D4) — which the stock simulator does not contain.

1 · Concepts primer

Everything the rest of the page assumes. Skip if you already know it; come back when a term is unfamiliar.

1.1 LLM inference: prefill vs decode

A transformer generates text in two phases. Prefill processes the whole prompt at once (many tokens, compute-heavy, parallel). Decode then emits one token at a time; for every new token the model must read all its weights again while doing only a few multiply-adds per weight. Decode is therefore memory-bandwidth bound: the cost of a step ≈ (bytes of weights read) ÷ (memory bandwidth), almost independent of how much math is done.

Batch size (B) helps because B requests share one read of the weights: bytes-per-token ≈ weights ÷ B. Decode at small batches is the worst case, and it is the regime the Duplex paper targets.

1.2 A Mixtral decoder layer

Mixtral-8×7B has 32 decoder layers, hidden size 4096. Each layer is:

  1. Attention: qkv_proj (4096 → 6144, i.e. Q 4096 + K 1024 + V 1024 — grouped-query attention), the attention itself, then o_proj (4096 → 4096).
  2. MoE block: a tiny router gate_fn (4096 → 8) scores the 8 experts; each token is routed to its top-2 experts. Each expert is a SwiGLU FFN with three matrices: gate_proj (4096 → 14336), up_proj (4096 → 14336), down_proj (14336 → 4096).
one expert = 3 × 4096 × 14336 = 176.18 M parameters = 352.3 MB in FP16 (2 bytes/param) per layer = 8 experts × 352.3 MB = 2.82 GB of expert weights whole model = 32 layers × 8 experts × 176.18 M = 45.11 B expert parameters

Mixtral's parameter budget: 45.11 B in experts + 1.34 B in attention (32 × (25.17 M qkv + 16.78 M o_proj)) + 0.001 B in routers + 0.26 B in embeddings ≈ 46.7 B total. At 2 bytes each that is 93.4 GB = 86.99 GiB of weights (Part 4 uses this exactly). Although 46.7 B parameters exist, only ~13 B are active per token — that is the whole point of MoE, and also why the unused weights are dead weight that still must be stored.

1.4 The roofline model

A kernel's time is max(compute time, memory time):

compute time = FLOPs / peak_FLOPS memory time = bytes / bandwidth arithmetic intensity (Op/B) = FLOPs / bytes "ridge point" = peak_FLOPS / bandwidth : the Op/B at which compute and memory time are equal

For an FP16 H100: ridge = 989.4 TFLOPS ÷ 3.352 TB/s ≈ 295 Op/B. A matrix-vector-like product with batch m reads k×n weights and does 2mkn FLOPs, so its arithmetic intensity is simply m (the number of rows/tokens) — far below 295 when m is small. That single fact is the MoE memory wall (Part 5). The simulator implements exactly this max() rule (linear_impl.cpp:61-62).

1.5 Processing-in-Memory (PIM) and Duplex

PIM puts limited compute inside or beside the DRAM so data does not have to travel to a distant core. Duplex (paper 2409.01141, in this folder) attaches both a GPU and a Logic-PIM die to the same HBM stacks: the GPU handles compute-heavy, large-batch work; the Logic-PIM handles the bandwidth-heavy, small-batch decode experts. Because both share HBM, no extra data movement is introduced. In the simulator this is processor_type: GPU+LOGIC. This is the configuration D1 reproduces.

1.6 Units you will see constantly

Simulator logs print nanoseconds (ns) for time and nanojoules (nJ) for energy; a value printed as GB is divided by 1024³, i.e. it is really GiB. Energy is quoted per bit (pJ/bit), so bytes×8×pJ/bit gives joules.

2 · The two simulators

Two independent, analytical simulators (no timing noise — they compute the roofline arithmetic directly, which is why re-runs are bit-identical) produce all raw data.

2.1 LLMSimulator — D1 and D3

LLMSimulator/ (upstream scale-snu/LLMSimulator, commit 4192527) builds a module graph of the model, and for each operator reports a fused time max(compute, memory) and an energy. Key behaviours:

  • Driven entirely by a YAML config; the model is model_name: mixtral.
  • Prints a per-device memory footprint (ACT / Weight / Cache) and a final Total: time in ns.
  • Exports one CSV per iteration into the config's output_directory.
  • With print_log: on it prints the full op tree of the run — this is the input to D3.
  • Routing is synthetic: uniform by default, Zipf-skewed if skewness > 0 (Part 6).

Its src/dram/ramulator2 submodule carries patch/ramulator2_pim.patch (the PIM support patch). All our configs use use_ramulator: off, so the cycle-accurate ramulator path is not exercised; the analytical roofline is what produces the numbers.

2.2 SSD-offloading — D2 load vs execution

SSD-offloading/LLMSimulator/ is a fork (upstream scale-snu/LLMSimulator, remote in this copy) with an offload model. It is used unmodified (only its own patches.sh, which applies two upstream patches). One boolean changes what the run measures:

ssd_cfgs/cpu.yamlonGPU execution of the experts: max(FLOPs/peak, bytes/(HBM_BW − link_BW)) — the copy contends with HBM, so HBM bandwidth is reduced by the link (hardware_config.h:97)

3.3 Why the footprints differ (26.07 vs 23.96 GiB)

The log prints the footprint of device 0 (cluster.cpp:222-226, via get_device(0)). Under the two parallel strategies:

These identities were checked against the printed values; the small residual is rounding in the model constants.

3.5 Details you must state correctly

  • iter: 3 writes only 2 CSV rows, because exportToCSV runs before each iteration and the last is never written (cluster.cpp:467-477). The two rows agree to ≤0.4%.
  • The energy gain is only 2.1% (3.228 → 3.160 J). Duplex's benefit here is latency, not energy.
  • 3.10× is above the paper's ~2.5× because this slice is decode-only (every CSV row has mixed=0), which is exactly the regime Logic-PIM accelerates. A mixed prefill+decode workload would show less.

D2 Single GPU, experts in off-chip DRAM

Asked: disable multi-GPU sharding and Logic-PIM, add off-chip DRAM, put all expert weights there, and report expert loading time and execution time.

4.1 Step 1 — the model does not fit in 80 GiB (LLMSimulator)

mixtral_single_gpu.yaml: 1×H100, processor_type: GPU, tensor/expert degree 1/1, batch 8, 512/32 tokens. The log says:

The weight figure is the parameter arithmetic of Part 1.2:

experts : 256 × 176.18 M = 45.11 B → ×2 B = 90.22 GB = 84.02 GiB attention : 32 × 41.94 M = 1.34 B → ×2 B = 2.68 GB = 2.50 GiB routers : 32 × 32.77 K = 0.001 B embeddings : 2 × 32000×4096 = 0.26 B → ×2 B = 0.52 GB = 0.49 GiB ──────────────────────────────────────────────────────────────── total : 46.7 B params × 2 B = 93.42 GB = 86.99 GiB ✓
This run sets exit_out_of_memory: off, so it continues although it does not fit. Because the weights alone (86.99 GiB) exceed HBM (80 GiB), the model does not fit at any batch size — the timings from this run are used only for D3's per-op op tree, never as a feasible single-GPU latency. H100 is used because the simulator only wires DRAM configs for H100/B100/B200 (device.cpp:34-39); an A100 run fails to load a config. H100 has the same 80 GiB capacity the brief names.

4.2 Step 2 — load vs execute (SSD-offloading framework)

Experts are placed in CPU memory (off-chip DRAM) and reached over NVLink-C2C 5.0 at 900 GB/s. Two configs differ in exactly one flag (full YAMLs in ssd_cfgs/); both: Mixtral, 1×H100, batch 4, one decode step over all 32 layers.

Configcollects_gpu_computeMeaning of expert_ffnResult
ssd_cfgs/cpu_copy.yamloffcopy routed experts CPU→HBM68.13 ms load
ssd_cfgs/cpu.yamlonGPU execution of the experts25.02 ms exec

Loading is 2.72× execution. analysis_d2.py re-derives both from first principles:

routed expert bytes moved = 61.31 GB (174 expert loads × 352.3 MB) how many loads? 4 tokens × top-2 × 32 layers = 256 slot-draws; expected distinct experts/layer = 8·(1 − (6/8)^4) = 5.47; measured 174/32 = 5.44 ✓ load = bytes / link BW = 61.31 GB / 900 GB/s = 68.12 ms (CSV 68.13) exec = bytes / (HBM BW − link BW) = 61.31 GB / 2452 GB/s = 25.00 ms (CSV 25.02) ratio = (HBM − link) / link = 2452 / 900 = 2.72× pure arithmetic = FLOPs / peak = 90.2 GFLOP / 989.4 TFLOPS = 0.091 ms ← 275× below exec energy: CPU→HBM copy 61.31 GB×8×13.4 pJ = 6.57 J HBM read 61.31 GB×8× 4.2 pJ = 2.06 J ratio 3.19× = 13.4/4.2

The energy constants are the framework's own: HBM read 4.2 pJ/bit; CPU-DRAM read 9.2 + HBM write 4.2 = 13.4 pJ/bit (module_graph.cpp:262-277). The expected-distinct formula: each token picks 2 of 8 without replacement, so P(a given expert is not picked) = 6/8 = 0.75; over 4 independent tokens, P(never picked) = 0.75⁴, so P(picked at least once) = 1 − 0.75⁴, and expected distinct = 8·(1 − 0.75⁴) = 5.47.

The single most important insight of D2. "Execution" is itself memory-bound: its arithmetic is only 0.091 ms, so 25.02 ms is pure HBM bandwidth. Load vs exec therefore reduces to link bandwidth vs HBM bandwidth — exactly the 2452/900 = 2.72× identity.

4.3 How to read the output (traps)

  • No expert caching: the framework assumes every decode step reloads every routed expert. That is the on-demand baseline the final phase improves on, not a bug.
  • In copy mode the framework also charges a copy for attention weights (qkvgen, o_proj), so use only the expert_ffn column, never MoE_decoders.
  • The link is C2C 5.0 (600 GB/s per direction class, 900 GB/s used here). A host CPU behind PCIe would be slower, so 2.72× is conservative.
  • All numbers reproduce with the framework unmodified — the invented "tier" patch was removed (Part 11).

5.2 The roofline replay — why one projection is 98× its math

The simulator reports one fused number per op, max(compute, memory). To separate them, analysis_d3.py replays the roofline for the first active expert's gate_proj, [3×4096] × [4096×14336]:

weight read = 4096 × 14336 × 2 B = 117.4 MB memory time = 117.4 MB / 3.352 TB/s = 35.036 µs ← measured 35.069 µs ✓ math = 2 × 3 × 4096 × 14336 = 352.3 MFLOP compute time = 352.3 MFLOP / 989.4 TFLOPS = 0.356 µs ratio = 35.036 / 0.356 = 98× → memory-bound arithmetic intensity = 352.3 MFLOP / 117.4 MB = 3 Op/B ( = the 3 tokens ) H100 ridge point = 989.4 / 3.352 = 295 Op/B → we are 98× below it

5.3 Why this makes loading the bottleneck

  • Expert size: one expert = 3 × 4096 × 14336 × 2 B = 352.3 MB; 8 per layer, 32 layers.
  • Too few tokens per expert: in decode each token picks 2 of 8 experts, so an expert sees only 1–3 tokens. Arithmetic intensity ≈ tokens-per-expert ≈ 1–3, enormously below the ridge of 295. Every projection is limited by reading its weights, not by computing.
  • No reuse across the batch: at batch 8, 7.28 of 8 experts are active per layer, so almost all expert weights stream every step.
  • Bandwidth gap: once experts live off-chip, their weights cross a 900 GB/s link instead of 3,352 GB/s HBM — which converts the memory-bound execution into the 2.72× loading cost measured in D2.
Quantitative summary. Over 32 layers, expertFFN = 96.2% of decoder time, with a mean of 7.28 of 8 experts active per layer. The per-op replay proves the time is weight reads: each projection's weight read is 98× its arithmetic. Loading is not slow because of latency or overhead — it is slow because the bytes are many and the tokens are few, and moving those bytes off-chip makes them cross a 3.7× narrower pipe.

D4 Temporal and spatial correlation of expert accesses

Asked: analyse temporal/spatial correlation in expert access with suitable plots and statistics.

6.1 Where the data comes from (stated plainly)

LLMSimulator ships no real routing traces. Its own routing has exactly two modes:

  • Uniform — getRandomExpert, the default (seed 777) scheduler.cpp:141.
  • Zipf-skewed — getZipfianRandomExpert with weights ∝ 1/(k+1)s scheduler.cpp:165, sequence.cpp:170.

analysis_d4.py generates both, plus one ST-MoE-like trace that adds layer-to-layer and token-to-token stickiness. That third trace is synthetic: its correlation is set by two knobs, so its numbers demonstrate the method, not a measurement of real Mixtral routing.

6.2 The generator (what the knobs mean)

per request: SEQ=64 requests × TOK=64 consecutive tokens × L=32 layers × top-2 uniform : each token draws 2 of 8 experts uniformly Zipf : draws from weights 1/(k+1)^s (s = 1.0) ST-MoE-like: PERSIST=0.7 → with prob 0.7 reuse the previous token's experts (temporal) STAY=0.6 → else, at layer l, keep each expert from layer l−1 with prob 0.6, otherwise redraw from Zipf (spatial); a collision redraws.

6.5 What the plot and table show

  • The simulator's default routing has no correlation: both overlaps sit on the 0.25 null and the transition matrix is flat.
  • Zipf skew creates spatial concentration (one expert takes 31.5% of accesses). Overlap rises to 0.36 — but only because hot experts recur by chance. For Zipf s=1, 2·Σp² ≈ 0.41; the without-replacement draw lowers the measured value to 0.36. The transition matrix shows vertical stripes, not a diagonal.
  • Only real temporal/spatial structure produces a diagonal transition matrix and overlap well above both: the ST-MoE-like trace reaches 0.556 spatial and 0.825 temporal. That diagonal is what an ST-MoE/APEX-style predictor exploits.
  • Coverage stays 6.5–7.2 of 8 in every case. Correlation can help predict which experts to fetch early, but it barely reduces how many must be fetched.
The finding that stands. The ST-MoE-like numbers are a property of the generator, and the page says so. The real result is about the simulator: its routing (uniform or Zipf) contains no temporal correlation, so any predictor must be evaluated on correlated traces fed to it. This is the honest foundation for the final phase's prefetching work.

8 · Simulator reference (facts for the viva)

  • Units: CSV times are ns, energies nJ (energy_nJ). Sizes printed as "GB" are divided by 1024³, so they are GiB.
  • One fused time per op: total = max(compute, memory) (linear_impl.cpp:61-62). Separate load from compute by replaying the roofline, as D3 does.
  • SSD-offloading reads ./config.yaml from the working directory in three places (linear_impl.cpp:47, hardware_config.h:170, module_graph.cpp:267). Passing a path on the command line does nothing — copy the config in first.
  • iter N writes N−1 CSV rows — export happens before each run (cluster.cpp:467-477).
  • Two different HBM energies: LLMSimulator uses the power model in power.h (HBM2E read 3.48 pJ/bit, power.h:32); SSD-offloading uses 4.2 pJ/bit (module_graph.cpp:262). Do not compare energies across the two tools.
  • Only H100/B100/B200 have DRAM configs (device.cpp:34-39); an A100 config fails to load.
  • offload_bandwidth level → link: 4 = NVLink 4.0 (450 GB/s), 5 = NVLink 5.0 (900 GB/s) (hardware_config.h:176-180).
  • Build trap: errors like "no member named filesystem/optional in std" mean the wrong compiler or C++ standard; force g++-11 and C++17. With GCC 13+ also add -DCMAKE_CXX_FLAGS="-include cstdint".
  • Analytical, not cycle-accurate: with use_ramulator: off there is no DRAM timing model, so repeated runs are bit-identical (verified in Part 10).

12 · Glossary and viva Q&A

12.1 Glossary

TermMeaning
MoEMixture-of-Experts: a layer with many "expert" FFNs; a router sends each token to a few.
ExpertOne SwiGLU FFN (gate/up/down) — 352.3 MB in Mixtral FP16.
Top-2 routingEach token is processed by its 2 best-scoring experts.
Decode vs prefillDecode = one token at a time (bandwidth-bound); prefill = whole prompt at once (compute-bound).
BatchNumber of requests served together; amortises weight reads.
HBMHigh-Bandwidth Memory, the GPU's on-package DRAM (H100: 80 GiB @ 3.352 TB/s).
Off-chip DRAMHost CPU memory, reached over NVLink-C2C (900 GB/s here).
PIM / Logic-PIMCompute placed at the memory; Duplex attaches a Logic-PIM die beside the GPU on the same HBM.
TP / DP / EPTensor / data / expert parallelism — how work (and weights) are split across devices.
Roofline / Op-BModel where time = max(compute, memory); Op/B = arithmetic intensity; ridge point = peak/BW (295 for H100 FP16).
OOMOut-of-memory: the model's footprint exceeds HBM.
pJ/bitEnergy per bit moved; ×8 converts bytes to bits for a joule figure.
GiB vs GBGiB = 1024³ bytes; the logs' "GB" is really GiB.

12.2 Viva quick answers

Why is a decode step bandwidth-bound?

Because each step re-reads all weights (46.7 B params = 86.99 GiB) for only a few tokens of work. Arithmetic intensity ≈ tokens per weight, far below the H100 ridge of 295 Op/B.

Why does MoE make it worse than a dense model?

Expert weights are huge (352 MB each) but each expert sees only 1–3 tokens, so arithmetic intensity drops to ≈1–3, and at batch 8 nearly all 8 experts are activated per layer — so almost every expert weight must be read every step.

What does Duplex change, and why is the speed-up 3.10×?

It adds a Logic-PIM die sharing HBM and enables parallel execution. On this decode-only slice the experts (96% of time) are served by the PIM instead of streamed to the GPU, and TP4 shards attention weights, giving 3.10×. Decode-only is Logic-PIM's best case; the paper's ~2.5× is a broader average.

Why does the model not fit on one GPU, and why H100 not A100?

Weights alone are 86.99 GiB > 80 GiB, so it OOMs at any batch. LLMSimulator only ships DRAM configs for H100/B100/B200; A100 would fail to load a config, and H100 has the same 80 GiB the brief names.

What exactly is the 2.72× in D2?

The ratio of "expert execution on GPU with a concurrent CPU→HBM copy" (25.02 ms) to "pure CPU→HBM copy" (68.13 ms). It reduces to (HBM BW − link BW)/link = 2452/900.

Is expert "execution" compute or memory bounded?

Memory: its arithmetic is only 0.091 ms, while the measured execution is 25.02 ms. Execution is HBM-bandwidth bound.

How many expert loads, and why?

174 = 5.44 distinct experts/layer × 32 layers for batch 4, top-2 — matching the analytic 8·(1 − 0.75⁴) = 5.47.

Why is one gate_proj 98× its math?

Reading 117.4 MB of weights takes 35.0 µs; the 352.3 MFLOP takes 0.356 µs. The op is memory-bound, and the simulator takes max().

What fraction of decoder time is experts?

96.2%, with a mean 7.28 of 8 experts active per layer.

Does the simulator's routing have correlation?

No. Its uniform and Zipf modes sit at the 0.25 overlap null. Only the synthetic ST-MoE-like generator (STAY/PERSIST) produces a diagonal transition matrix and high overlap; that trace tests the analysis method, not real routing.

Can correlation reduce how many experts must be fetched?

Barely — coverage stays 6.5–7.2 of 8 across all scenarios. Correlation helps predict which to fetch early (prefetch), not how many.

Why are re-runs bit-identical?

With use_ramulator: off the simulator is pure roofline arithmetic — no timing randomness — so the build/runs reproduce exactly (Part 10).

Why does iter 3 give 2 CSV rows?

Export happens before each iteration, so the final iteration is never written (cluster.cpp:467-477). The two rows agree to ≤0.4%.

Why can't you compare energies across the two simulators?

They use different HBM energy constants: LLMSimulator's power model 3.48 pJ/bit vs SSD-offloading 4.2 pJ/bit.
